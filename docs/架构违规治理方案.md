## 一、动手前必读：修复方案本身不能引入新违规

⚠️ 这是基线文件 D-668 记录的真实踩坑，**决定了每项能用什么修法**：

> 🔴 为什么**不**改叫 `*Orchestrator`：调用方是 Service 层，移入 `production.orchestration`
> 会形成「Service 层反向依赖 Orchestrator 层」→ 违反分层方向，故只能归 helper。

### 判据：先看调用方在哪一层，再决定修法

```
调用方中有 Service  →  只能改 *Helper（移入 helper 包）
                      否则 Service → Orchestrator = 反向依赖 = 新违规

调用方全是 Orchestrator / Controller / Job  →  可改 *Orchestrator（移入 orchestration 包）

调用方里有 Controller  →  ⚠️ 上移编排后 Controller 需同时依赖 Orchestrator + 剩余 Service
                         超过 1 个 Service 就撞规则6（Controller 不得依赖多个 Service）
                         此时只能改 *Helper（见 D-662 DailyBriefingHelper 的先例）
```

**规则6 是"字段数 > 1"才违规**，所以保留 1 个 Service 是合法的省事做法（D-645 ScanRecordController、D-647 EcommerceOrderController 均用此法）。

### 已验证的 5 种修复模式（沿用历史，勿自创）

| 模式 | 做法 | 历史先例 |
|------|------|---------|
| 1. 死代码删除 | 全仓零引用直接删 | D-656（删 2 个）、D-657（删 1 个） |
| 2. 改名移 helper | 工具型/纯函数 → `*Helper` + 移入 `helper` 包 | D-658、D-660、D-662、D-667、D-669 |
| 3. 上移编排 | 多源聚合 → `*Orchestrator` + 移入 `orchestration` 包 | D-657 WechatWorkNotifyService、D-661、D-663 |
| 4. 简化接口 | 抽 DTO 消除依赖 | D-643 PayeeSearchResult |
| 5. 移入 common | 基础设施 → 既有豁免包，**判据零改动** | D-659 QdrantService、D-670 AuthTokenService |

## 二、21 项完整清单（按治理性价比排序）

排序依据来自基线 D-655 的判据：
> **规则7 按类计数**，该类依赖 8 个 Service 也只产生 1 条违规 ——「依赖数」衡量的是重构**成本**而非**收益**。
> 选起点应优先「**依赖数少 + 调用方少**」的类。

#### A4. `MaterialStockServiceImpl` + `MaterialPickingServiceImpl` + `MaterialPurchaseServiceImpl` → 🔴 **移入 C 类，不要动**

这三项构成一条链：

```
MaterialPurchaseServiceImpl ──→ MaterialStockService
MaterialPickingServiceImpl   ──→ MaterialStockService
MaterialStockServiceImpl     ──→ MaterialDatabaseService
```

| 类 | 依赖数 | 调用方 | svc 调用方 |
|---|--------|--------|-----------|
| `MaterialStockServiceImpl` | 1 (`MaterialDatabaseService`) | 27 | **3** ⚠️ |
| `MaterialPickingServiceImpl` | 1 (`MaterialStockService`) | 16 | 0 |
| `MaterialPurchaseServiceImpl` | 1 (`MaterialStockService`) | 57 | **5** ⚠️ |

**性质判定（2026-10-01 逐处核实）**：三项均为**库存增减的核心写路径** ——
`MaterialPickingServiceImpl:78` 的 `decreaseStockById / decreaseStock`、
`MaterialPurchaseServiceImpl:212` 的 `increaseStock`、`MaterialStockServiceImpl` 的
`decreaseStockWithCheckDecimal` 抛异常前的整段逻辑。

⚠️ **勘误**：本节初版写作「都是 `@Transactional` 内的跨服务业务写操作」，
经核实**这三个文件 `@Transactional` 出现次数均为 0**（`MaterialPickingServiceImpl` /
`MaterialPurchaseServiceImpl` / `MaterialStockServiceImpl`），理由不成立，已删除。
事务归属在编排层（见下方「与事务核实报告的关系」）。

**真正的排除理由（两条，均可验证）**：
1. **调用方规模** —— `MaterialPurchaseServiceImpl` 57 个调用方（svc 调用方 5）、
   `MaterialStockServiceImpl` 27 个（svc 3），改名/移包需同步数十处 import，
   而规则按类计数，收益仅 -1；
2. **业务敏感性** —— 这是库存增减的核心写路径，改动直接影响生产出入库，
   风险与收益完全不成比例。

**结论**：三项整体移入 C 类（不要碰）。⚠️ `MaterialPurchaseServiceImpl` 有 57 个调用方，
单看「依赖数 = 1」会严重低估风险 —— 这是「依赖数衡量的是成本而非收益」的反面例证。

> **与事务核实报告的关系**：追这条链时另发现一个**独立的 P0 缺口** ——
> `MaterialPickingOrchestrator.createPicking()` 与 `MaterialPickingTool` 走的旁路
> 做 4 个写操作（含扣库存）却**全程无事务**，中途失败会产生
> 「领料单 completed + 明细缺失 + 库存已扣」的脏数据。
> 主流程（`createPickingAndOutbound`）有 `@Transactional`，不受影响。
> 详见 [领料出库事务边界核实报告.md](领料出库事务边界核实报告.md)。

## 五、我的结论

1. **架构整体健康，5/6 类违规已清零，剩下 1 类在有序收敛**（56 → 21，且 35 个 Controller 已清零）
2. **21 项 ≠ 21 件事**：真正低风险的只有 6 项（A1-A3 + B1-B3），71%（15 项）属高调用方类或事务写链，不建议动
3. **ratchet 机制有效**，不追求清零是合理工程决策 —— 基线注释里写得很清楚：
   > 存量代码已有大量违规……若直接写死规则，CI 会天天红逼着人加 `-DskipTests` 绕过 —— **比假绿灯更糟**。
4. **建议目标：降到 15 即停**，剩余用 ratchet 长期收敛
