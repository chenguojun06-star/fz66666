## 一、执行摘要

系统**没有资源瓶颈**（负载 0.06、CPU 7%、内存 797MB/2GB、库 808MB），
真正的低效集中在三处：

1. **AI 输出长度失控**（已修）：QuickPath 单次 56-82 秒，真凶是输出跑满 2048 token
2. **可观测性缺失**（本批修）：只有"完成时间"，没有首字/分段耗时，无法定位"检索慢还是生成慢"
3. **AI 日志表失控增长**（待决策）：`t_intelligence_audit_log` 42.7 万行占**全库 61%**（493MB）

## 二、问题诊断

### 2.1 应用层 — 小云响应（数据定位，非推测）

| 证据 | 数值 | 来源 |
|---|---|---|
| Agent 执行次数（近30天） | 17 次，其中 **16 次 56-82 秒** | `t_agent_execution_log` |
| scene 分布 | 全部 `quick`（QuickPath） | 同上 |
| 后台任务（近30天） | 421,955 次，全 SUCCESS | `t_ai_job_run_log` |
| 自动巡检 | 16,979 次 | `t_ai_patrol_action` |
| 人机对话使用率 | 极低（30 天 17 次） | `t_agent_session` 近 7 天为 0 |

**逐段排除（这是关键，避免误判）**：

| 环节 | 结论 | 依据 |
|---|---|---|
| 上下文构建（RAG/记忆/经营/实体） | ❌ 不是瓶颈 | 四路并行 + `.get(4, TimeUnit.SECONDS)` 硬上限，≤4s |
| 工具轮次（5 轮 × 15s） | ❌ 不是瓶颈 | QuickPath 不带工具；业务问题才降级 Agent（D-702 正确取舍：宁可慢不可假） |
| 流式阻塞 | ❌ 不是瓶颈 | `chatStream` 真流式，`chunkConsumer.accept` 逐片推前端 |
| **输出长度** | ✅ **真凶** | `resolveMaxTokens("ai-advisor")` 默认 **2048**；deepseek-flash 约 30-45 token/s → 跑满即 50-70s |

**已修（D-856）**：`ai-advisor` 2048→**1024**、`agent-loop` 4096→**3072**，并加软约束（先结论、300 字内），两者可配置。

### 2.2 数据层 — 存储与增长

| 对象 | 规模 | 占比 | 判断 |
|---|---|---|---|
| 全库 | 319 表 / data 407MB + index 401MB = **808MB** | — | 规模正常 |
| `t_intelligence_audit_log` | **42.7 万行 / 493MB** | **61%** | ⚠️ 单行约 1.2KB，增长快 |
| `t_ai_job_run_log` | 66 万行 / 161MB | 20% | ⚠️ 日志型大表 |
| `t_intelligence_signal_bak_d702` | 15 万行 / 51MB（**无索引**） | 6% | 🗑 历史备份残留 |
| 其他 bak 表 | 4 张（bak_d744 / _bak_d654 / bak_d719 ×2） | <1% | 🗑 备份残留 |

**核实：清理任务不是"做了没接"**——`AuditLogCleanupJob` 已接且每天 4:50 跑（`@Scheduled`），
保留期 90 天。表仍大是因为**产生速率高**（约 4700 行/天）且单行体积大。

## 五、方法论沉淀（本项目反复验证有效）

1. **先数据后调优**：本次若直接"降轮次/降超时"，会牺牲准确性（D-702 的教训）——数据证明瓶颈在输出长度，两者结论完全不同
2. **逐段排除而非整体猜测**：上下文/工具/流式/输出 四段分别取证，才锁定真凶
3. **改完必须跑测试**：本批首版 `@Value` 注入 Map 导致启动失败（9 个测试报错），跑测试才暴露
4. **不留静默吞异常**：本次所有 catch 都补了 `console.warn`/日志，避免新的排查黑洞
5. **不完善验收掩盖失败**：耗时改善无法用单测证明，已在多处如实标注"待实测"
