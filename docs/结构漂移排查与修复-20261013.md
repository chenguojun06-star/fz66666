# 生产库结构漂移：排查与修复（2026-10-13）

## 一句话结论

**生产库的真实结构与代码期望不一致，而所有静态检查都是绿的。**
根因是「库被还原/重建过，但 Flyway 记录还在」+「应用自带一套运行期建表 DDL（第二份真相）」。
本次修好 6 处会影响线上功能，清掉 3 组死代码，并补了一个能提前发现这类问题的检查脚本。

## 怎么发现的

用户让查服务器错误 → 从 `docker logs` 里翻出两条 ERROR，其中一条是
`Unknown column 'pattern_type'`。顺着它把生产库 304 张表的真实列全部导出，
与 259 个 `@TableName` 实体逐字段比对，才看到全貌。

**为什么原来的检查没拦住**：

| 检查 | 比的是什么 | 为什么漏了 |
|---|---|---|
| `check-entity-flyway.py` | 实体 vs 迁移脚本 | 两边都自洽就 PASS，而真正错的是**库** |
| `check-flyway-column-deps.py` | 迁移脚本内部引用 | 同上 |
| `SpringContextSmokeTest` | Bean 能否创建 | 表结构问题不在启动期暴露 |
| 全部单测 | 逻辑 | Mapper 全是 mock，**没有一条 SQL 真的打到库上** |

## 三类漂移

### 一、Flyway 以为建了，库里根本没有（4 张）

`flyway_schema_history` 里这些迁移全部 `success=1`，但表不存在：

| 迁移 | 声明的表 | 库里 |
|---|---|---|
| V202604301004 | `t_ai_operation_audit` | ✗ 不存在 |
| V31 | `t_express_order` | ✗ 不存在 |
| V25 | `t_logistics_track` | ✗ 不存在 |
| V202704271320 | `t_material_roll` | ✗ 不存在 |

**为什么**：库在某次还原/重建时丢了这些表，Flyway 记录还留着。已 applied 的迁移
**永远不会重跑**，所以表再也回不来 —— 这类问题没有任何"自愈"机制。

**影响**（都是一调用就 500）：

- `/api/express-order/**`（`ExpressOrderController`）
- `/api/production/material/roll/**`（`MaterialRollController`）
- 智能巡检的物流轨迹（`IntelligenceAdvancedController` → `LogisticsTrackingOrchestrator`）
- AI 操作审计（`AiOperationAuditOrchestrator`）

> 顺带一提：我一开始用「反向引用可达性」脚本判断这些是不是死代码，脚本判成了"不可达"，
> 但它们其实都有 `@RestController`。**启发式脚本会骗人，结论必须手工复核一遍。**

### 二、表在但列不全（3 张）

`CREATE TABLE IF NOT EXISTS` 遇到已存在的（旧结构）表会**直接跳过**，
所以老结构的表永远长不出新列：

| 表 | 缺的列 | 影响 |
|---|---|---|
| `t_pattern_discovery` | 15 列 | 模式发现定时任务每轮报错（已修，见下） |
| `t_goal_decomposition` | 16 列 | 目标拆解（`AutonomousAgentController`） |
| `t_agent_memory_core` | 3 列 | 智能体记忆（`AgentMemoryService`/`MemoryBankService`） |

`t_agent_memory_core` 还多一层：老结构的 `key` / `value` 是 **NOT NULL 且无默认值**，
而实体与两个 Service 用的都是 `agent_id` / `memory_key` / `memory_value` ——
INSERT 根本不带 key/value，不放开可空就会报 `Column 'key' cannot be null`。

### 三、死代码（3 组，已删）

全仓零引用（没有 Controller、没有定时任务、没有任何调用方）：

- `LogisticsProvider`（entity + mapper + service + impl）
- `UnitPriceAuditLog`（entity + mapper + service + impl）
- `OrderFulfillmentOutcome`（entity + mapper）

删掉它们同时消掉了 3 个「表不存在」的雷。

## 修复动作

### 1. 迁移 `V202710130001__fix_pattern_discovery_columns.sql`

补 `t_pattern_discovery` 的 15 列。**已在克隆库上三场景验证**：
漂移库 6→21 列、重复执行无副作用、全新库零报错；随后手动应用到生产。

### 2. 迁移 `V202710130002__create_missing_tables_and_fix_drift.sql`

- 建 4 张缺失表（列定义以**实体**为准：主键是 String + `ASSIGN_ID`/`ASSIGN_UUID`，
  不是老迁移里的 `BIGINT AUTO_INCREMENT` —— 实体改过、迁移没跟）
- 补 `t_goal_decomposition` 16 列、`t_agent_memory_core` 3 列
- 放开 `t_agent_memory_core.key/value` 为可空

沿用 V38 的 `information_schema` 守卫 + 动态 DDL 写法，幂等。

### 3. 修 `MyBatisPlusMetaObjectHandler`（P0，与漂移无关但同批发现）

MyBatis-Plus 对声明了 `@TableField(fill = ...)` 的字段会**无条件**写进 INSERT
（不受 `NOT_NULL` 策略保护）。处理器只填了 `createTime/updateTime`，
漏了另一套命名的 `createdTime/updatedTime` → 落库是显式 NULL →
`created_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP` 不走默认值，直接报错。

后果：支付回调日志写不进去（整条回调 500）、`t_payment_record` 落流水同样失败
（**商家配好商户号后第一次收款就会失败**）。

新增 `MetaObjectFillGuardTest`：扫全部实体，凡声明 `fill` 的属性，处理器必须有对应填充。

### 4. 新增 `scripts/check-entity-db-drift.py`

拿实体声明的列去比**真实库**的列，缺表/缺列直接非 0 退出。支持直连（需 pymysql）
或离线 TSV（适合只读导出生产）。

## 仍然存在、但暂不处理的

1. **`DbTableDefinitions` 是第二份真相**（74 张表的 Java 内置 DDL）。本次漂移的
   直接来源之一就是它。彻底解法是退掉它、只留 Flyway，但涉及 74 张表，风险大，
   建议单独排期。当前它只在"表不存在时"才动手，所有表都在 → 处于休眠状态。
2. **其中 3 张表的 Java DDL 已经过时**（`t_secondary_process`、
   `t_order_decision_snapshot`、`t_order_learning_outcome`）—— **已修**：
   按线上 `SHOW CREATE TABLE` 重写了这 3 段定义。修之前的状态是：
   库里是更新的结构（比如 `t_order_learning_outcome` 线上 21 列、
   Java 定义里那 4 列一个都不存在），因为表都在所以 `IF NOT EXISTS` 什么都不做、
   表面无害；但**万一这些表被删，应用会用错的形状重建它们**。
   现在 74 段内置 DDL 与线上逐列一致。
3. **LLM 输出被截断**导致 JSON 解析失败（CEO 智能体/模式发现），已 catch 记录，
   属健壮性问题。

## 教训

1. **审计必须连真实数据库一起审**。"实体 vs 迁移"自洽不等于"库 vs 实体"自洽。
2. **`CREATE TABLE IF NOT EXISTS` + 已 applied 的迁移 = 永久漂移**：只要有人带外改过库，
   这个迁移就再也不会纠正它。带外改库是漂移的温床。
3. **`fill` 是"必须填"的承诺**，不是"可以填"的建议；字段名有变体（`createdTime` vs
   `createTime`）时最容易漏，而单测（Mapper 全 mock）永远抓不到。
4. **生产 DDL 先在克隆库上按真实形状试跑**（漂移库 / 重复执行 / 全新库三种），
   比"相信迁移写对了"可靠得多。
5. **启发式分析要复核**：反向引用可达性脚本把 3 个有 Controller 的类判成了死代码。
