**重要**：现在下单/取消/查轨迹/运费报价**全部被拦截并明确报"不可用"**。
这是刻意的止血（原先返回的是 `"SF"+时间戳` 这类假运单号，会被回传电商平台污染真实订单）。
所以"填上密钥就能用"并不成立——**适配器方法体本身也是空的**，两家有骨架的也一样。

### 已完成的止血改造（2026-09-23）

把"假数据"从代码里彻底清掉了，现在 8 家适配器是 **fail-closed（未实现即显式报不可用）**：

| 改动 | 说明 |
|------|------|
| 新增 `AbstractLogisticsAdapter` | 基类：5 个能力默认全部抛"未接入"异常，`isRealImplementation()` 默认 `false`。子类**只能靠覆写来放行**，无法"忘记实现却返回数据" |
| 8 家适配器全部精简 | 删除约 400 行重复的 Mock 代码（`"SF"+时间戳` 假运单号、写死运费、编造轨迹、`return true`），每家只剩渠道标识 ~30 行 |
| 双层防护 | ① 适配器层 fail-closed；② `LogisticsManager.requireRealChannel` 守卫。任一层被绕过，另一层仍拦得住 |
| 守护测试 | `LogisticsAdapterFailClosedTest`：遍历全部 8 家，断言"未实现的渠道调用必须抛异常、地址校验不得声称可达"。**任何人重新塞 mock 返回值就会测试失败** |
| 集成中心改真话 | 原先把物流渠道显示成"模拟模式（可用）"，现改为「接口未接入」红色状态 + 禁用配置按钮（避免运营误以为填密钥就能用）；8 家全部登记，未建回调端点的显示"待接入时创建" |

> 注意：**支付渠道的 Mock 模式仍然保留**（密钥未配置时返回 `MOCK_` 前缀响应），
> 所以集成中心的状态判定对物流/支付是分开的——物流看"代码是否实现"，支付看"密钥是否配置"。

## 二、通用前置条件（缺一项都推不动）

| # | 前置条件 | 说明 | 当前 |
|---|---------|------|------|
| 1 | **企业资质** | 营业执照、法人身份证正反面、统一社会信用代码、对公账户。快递开放平台基本不对个人开放完整功能 | 需确认 |
| 2 | **与快递公司签"协议客户/月结"合同** | ⚠️ 关键：**电子面单必须有快递公司分配的"电子面单账号 / 客户编码"**，没有它连聚合平台也开不面单 | 需确认 |
| 3 | **公网可访问的 HTTPS 域名** | 用于配置 `notify-url`（物流状态回调）。必须是外网可达的正式域名，不能用内网 IP / localhost | 需确认 |
| 4 | **服务器出口 IP** | 部分平台需报备 IP 白名单，否则请求被拒 | 需确认 |
| 5 | **回调端点** | 每家一个 `POST /api/webhook/logistics/{code}`，需在快递后台登记 | 只有 SF/STO |

> 第 2 条是最容易被低估的一条。很多团队以为"申请个开放平台账号就能打单"，
> 实际电子面单的**面单额度与账号来自快递公司网点/客户经理**，开放平台只是接口通道。

| 代码接入点 | `integration/logistics/impl/SFExpressAdapter.java`（方法体待实现）+ `SFExpressProperties` |
| 沙箱 | https://sfapi-sbox.sf-express.com/std/service |
| 签名 | ✅ 已按官方规则修正：`Base64(MD5(msgData + timestamp + checkWord))`，**appKey 不参与**，已加单测守护（`SignatureUtilsTest`） |

> **签名这一项已经修过了，但拿到账号后仍要实测一次。**
>
> 原实现把 appKey 也拼进待签字符串（`msgData+timestamp+appKey+checkWord`），与官方规则不符。
> 这个 bug 的可怕之处在于——**即便密钥完全正确，请求/回调也会被拒**，现象极像"密钥填错了"，
> 排查成本很高。现已按官方文档的**代码示例**修正为 `msgData+timestamp+checkWord`。
>
> ⚠️ 但顺丰官方文档正文给的示例输出**与其自身代码示例矛盾**：按公式算不出它写的那个值，
> 穷举三种元素全部 6 种拼接顺序也都不匹配，判断是该示例未随规则更新。
> 所以单测只绑定"公式形态"，不绑定那个示例值。
> **拿到顺丰账号后，请用开放平台的「数字签名鉴权测试工具」实测一次确认**（文档页内有入口）。

## 五、代码侧待办（按接入顺序）

接入某一家时，完整要做 5 件事（缺一不可）：

1. **配置类** — 新建 `{Carrier}Properties`（`@ConfigurationProperties`）+ `application.yml` 段
2. **签名方法** — 在 `SignatureUtils` 加 `build{Carrier}Signature()`，**用官方文档给的测试向量写单测**
3. **适配器实现** — 替换 `{Carrier}Adapter` 的 5 个方法（createShipment / cancelShipment / trackShipment / estimateShippingFee / validateAddress），走 `IntegrationHttpClient`
4. **`isRealImplementation()` 返回 true** — 这一步做了，`LogisticsManager` 的守卫会自动放行该渠道
5. **回调端点** — 新建 `POST /api/webhook/logistics/{code}`：验签 → 状态映射 → `updateLogisticsStatus` → 签收时 `onLogisticsDelivered`

> 第 4 步是这套止血设计的关键：**真接入 = 显式声明**，不需要回头改管理器。

## 六、建议推进顺序

1. **先定路线**：8 家直连 vs 聚合平台（快递100 / 快递鸟）
   - 直连：一家一个合同 + 一套签名 + 一个回调，工作量大，但可控、无中间费用
   - 聚合：一次接入覆盖几十家（快递鸟称支持 2700+ 快递查询、60+ 面单），但**电子面单仍需快递公司/网点面单账号**，且多一层中间服务与费用
   - 建议：**主力 1~2 家直连**（发货量最大的），**长尾走聚合**
2. **首选顺丰做通**：配置类、回调端点、签名骨架都已有，改造量最小，能最快跑通"下单→面单→轨迹回调→签收回写"全链路
3. **跑通后复制到申通**（回调已实现，最省事）
4. 其余按发货量排序推进；每接一家补一份签名测试向量
