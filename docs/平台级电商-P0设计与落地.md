# 平台级电商 · P0 设计与落地说明

> 决策前提（2026-10-09 用户拍板）：**资金各租户直收，平台不抽成**（走方案 B）。
> 平台只做「公共商城 + 引流 + 账号」，不碰钱、不做分账。

## 一、P0 要解决什么

把 D-763 的「每租户一个独立小店」升级为**平台方运营的公共商城**：

| 维度 | P0 之前（D-763） | P0 之后 |
|---|---|---|
| 入口 | `/shop/index.html?s={slug}`，一租户一店 | 新增 `/shop/platform.html` 平台首页（跨店商品池），店铺页降级为「平台里的一家店」 |
| 身份 | 免登录，手机号即身份 | **平台级 C 端账号**（手机号 + 密码，一人一号、跨店通用），与免登录**并存** |
| 商品 | 只查本租户 `shop_listed=1` | **跨租户商品池**（搜索 / 类目 / 店铺维度） |
| 收货地址 | `t_shop_address`（租户 + 手机号） | 新增 `t_shop_consumer_address`（平台级，跨店复用）；旧表保留不动 |
| 订单 | 一单只含一个租户 | 不变（一单仍只含一个店铺 —— 资金各店直收的必然结果） |
| 平台方 | 无 | 只读总览：店铺 / 在架商品 / 注册用户 / 订单计数 + 最近订单 |

## 二、数据模型（迁移 `V202710090002__create_platform_shop_consumer.sql`）

- `t_shop_consumer`：平台级 C 端账号（**无 tenant_id**，手机号全局唯一）
- `t_shop_consumer_address`：平台级收货地址簿（**无 tenant_id**）
- `t_shop_order.consumer_id`：登录用户下单时写入，支撑「我的订单（跨店）」

两张新表**刻意不带 tenant_id**，并已在 `TenantInterceptor.EXCLUDED_TABLES` 登记为全局表
（否则带租户上下文查询会拼出 `AND tenant_id = X`，而该列并不存在 → SQL 报错）。
`scripts/audit-tenant-id.py` 的豁免清单也同步登记了 `ShopConsumer*`。

## 三、身份与令牌（关键安全设计）

消费者令牌与员工令牌是**两套身份**：

1. 消费者令牌走独立请求头 `X-Shop-Token`，`TokenAuthFilter` 根本不读它；
2. 令牌内 `roleName = shop_consumer`，且 `TokenAuthFilter` **显式拒绝**该角色 ——
   即使有人把消费者令牌塞进 `Authorization`，也拿不到「已登录员工」身份。
   （判据常量放在 `SecurityConstants.SHOP_CONSUMER_ROLE`，避免 auth → shop 反向包依赖。）
3. 令牌有效期 30 天，无刷新令牌（C 端无资金操作，体验优先）。

## 五、跨租户只读查询

`ShopPlatformMapper` 类级 `@InterceptorIgnore(tenantLine = "true")` 绕过租户拦截器
（与 `IntelligenceProcessStatsMapper` 同一做法），只提供 SELECT，且不含成本/供应商等内部字段。

## 六、刻意**不做**的事（避免越界返工）

- ❌ 平台代收 / 分账 / 佣金：用户已明确「资金各租户直收，平台不抽成」
- ❌ 跨店购物车 / 拆单：一单仍只含一个店铺
- ❌ 平台运营后台的**写**能力（商品审核、类目管理）：留待 P2，权限边界定型后再开
- ❌ 短信验证码登录：`SmsLoginHelper` 已具备能力，但未开通短信网关时不可用，故 P0 用密码登录

## 七、P1（本轮已实现）：跨店购物车 + 结算拆单 + 订单详情

| 能力 | 实现 |
|---|---|
| 跨店购物车 | `t_shop_cart_item`（**挂在 consumer_id** 下，`(consumer_id, sku_id)` 唯一；`tenant_id` 只作结算分组键） |
| 加购 | 服务端校验：SKU 存在 / 款式在架 / 库存充足；同 SKU **累加**而非插两行 |
| 失效商品 | 下架 / 打烊 / 缺货的行**照常返回**并带 `available=false` + 可读原因，绝不静默消失 |
| 结算 | `POST /api/shop/public/me/checkout` —— **按店铺逐张下单**，一张订单只含一个店铺 |
| 失败隔离 | 每店独立事务；某店失败**不影响其他店**，失败店铺的商品**留在购物车**待重试 |
| 订单详情 | `GET /api/shop/public/me/orders/{orderNo}` —— 明细 + 物流 + 售后状态，**必须同时匹配 consumerId** |

接口一览（均在 `/api/shop/public/me/**`，身份走 `X-Shop-Token`）：

- `GET /me/cart`、`POST /me/cart`、`POST /me/cart/{id}/quantity`、`POST /me/cart/{id}/delete`、`POST /me/cart/clear`
- `POST /me/checkout`（body：`customerName / phone / address / remark / tenantIds`）
- `GET /me/orders/{orderNo}`

## 八、P2（本轮已实现）：买家售后 + 商品评价

### 8.1 买家售后（补上闭环断裂的那一半）

此前售后只有**商家代顾客登记**的入口（`ShopAdminController` 的 after-sale/apply）——
顾客收到有问题的货，在系统里无处发起，只能打电话，商家再手动登记。
状态机（`APPLIED → APPROVED/REJECTED`）早就有了，缺的是「APPLIED 由谁触发」。

- `POST /api/shop/public/me/orders/{orderNo}/after-sale`（body：`type` / `reason`）
- 只有**已发货**订单可申请（未发货提示走取消订单）；`APPLIED`/`APPROVED` 时不可重复申请，
  `REJECTED` 后允许再申请
- 审批仍走商家侧既有逻辑，**不重复实现**库存回补与应收冲销

### 8.2 商品评价

- 表 `t_shop_review`：粒度 **一单一款一条**（`order_id + style_no` 唯一）；
  带 `tenant_id`（商家查自己店铺评价仍走租户隔离）
- 规则：只有已发货订单可评价；款式必须在该订单里；星级 1~5；内容 ≤ 500 字；
  **提交后不可修改**（防刷分）
- `POST /api/shop/public/me/orders/{orderNo}/reviews`
- `GET /api/shop/public/platform/styles/{styleId}/reviews` —— 公开可读的均分 + 条数 + 最新评价
- 商品池卡片展示 `★4.5 (12)`；平台商品弹层展示最新评价；订单详情里逐款评价 / 显示「已评价」

## 九、P2 补齐（本轮）：买家取消订单 + 商家看评价 + 排序 + 平台全站商品

### 9.1 买家取消未发货订单

与买家售后**同一类断裂**：取消订单的实现（回补库存 + 撤销应收 + 状态留痕）早已完整，
但入口只在商家侧。顾客下错单、地址填错，在系统里取消不了。

- `POST /api/shop/public/me/orders/{orderNo}/cancel`
- 复用而非重写：按订单真实租户构造上下文，直接调用商家侧既有 `cancelOrder`，
  行为/台账/操作日志与商家自己取消**完全一致**（日志操作人显示「买家xxxx」）
- 抽了 `ShopTenantContextRunner` 统一「以指定租户身份执行」，下单与取消共用一份实现

### 9.2 商家侧商品评价

评价此前只有 C 端写入、**没有任何商家侧读入口** —— 数据有了但没人消费等于白做。

- `GET /api/shop/admin/reviews`（分页，可按款号 / 星级过滤）
- `GET /api/shop/admin/reviews/summary`（均分 / 总数 / 各星级分布）
- 响应体**不含 consumer_id**（对商家无意义且属顾客隐私）
- PC 端「店铺管理」新增「商品评价」页签

### 9.3 商品池排序

- `/api/shop/public/platform/products?sort=newest|price_asc|price_desc`
- 排序值走**白名单**（非白名单一律回落最新），不把用户输入当 SQL 语义
- 价格在 SKU 上，排序走 `MIN(sales_price)` 子查询；未维护售价的用 `COALESCE` 兜到最后

### 9.4 平台方查看全站在架商品（只读）

- `GET /api/shop/admin/platform/products`（跨租户分页，仅平台超管）
- 只读：下架/审核属于会改变租户既有上架行为的动作，需先定策略（是否强制审核、
  下架如何通知商家）再开，避免越权改别人数据

## 十、本轮（接手在制改动 + 四件收尾）

### 10.1 接手「浏览行为 + 商品推荐」（原 D-784，工作区里的半成品）

工作区里已有一份**写了但完全没接线**的实现（无控制器、无调用方、无测试），
核心策略（同品类 / 个人偏好 / 热度三级混合 + 时间衰减）是可用的，直接接手而不是重写：

- 迁移版本归位：`V202612120001` → `V202710100002`（原版本号比已应用的迁移还早，
  虽然 Flyway 配了 `out-of-order: true` 能跑，但新脚本挂在历史版本上迟早出事）
- **接线**：详情页 `productDetail(slug, styleId, consumerId)` 记录浏览；
  新增 `GET /{slug}/products/{styleId}/recommendations`；顾客端详情页底部「猜你喜欢」
- **浏览记两件事**：① 按天计数（匿名也记，看板要用）② 个人明细（仅登录顾客）——
  匿名没有稳定身份，建档即垃圾数据
- 推荐**只推本店**：跨店会把顾客带离当前店铺，而订单不跨店（各租户直收）

### 10.2 平台一键下架 + 通知商家（平台治理）

口径：**发布即上架 + 事后巡检 + 违规下架**，不做前置审核（前置审核会让商家上架变慢、
平台还要背审核人力，主流平台现在也不这么做）。

- `POST /shop/admin/platform/listing/takedown`（必填原因）+ `/listing/relist`
- 平台**只改 `shop_listed`**，不碰商品资料 —— 权限边界是「能不能卖」
- 下架原因随通知发给**该商品所属租户**（新增 `SysNoticeOrchestrator.sendToTenant`），
  不告诉商家为什么，商家只会反复重新上架
- 平台商品列表**含已下架**（否则下架之后就没法恢复了）

### 10.3 类目统一为中文词表

线上平台首页的类目一度是 `WOMAN / 上衣 / SKIRT / 旗袍 / JACKET / DRESS` 中英混排，
根因是类目取的是款式资料里的**自由文本**字段。

- 新增 `ShopCategorySupport`：规范代码 + 中文名 + 别名（含代码本身与中文名）
- 展示一律转中文；筛选按**别名集合**（`IN`）—— 筛「半身裙」同时命中 `SKIRT/JUPE/半身裙`，
  老数据一个不漏
- **不批量改库**：`category` 是生产/裁床等模块共用的字段，改库风险远大于收益
- 上架编辑页新增「商品分类」下拉（同一份词表），新数据不再继续混

### 10.4 店铺数据看板（日报）

只做四个数：**浏览 → 加购 → 下单 → 下单金额**（不做漏斗/归因/同比，档口老板不看那个）。

- 新增 `t_shop_stat_daily` 计数器：购物车行结算后会被删、浏览日志按顾客+款式合并，
  这两项事后都还原不出按天的数，必须独立计数（`ON DUPLICATE KEY UPDATE` 累加防并发丢数）
- 下单与金额**实时查订单表**：能从事实表算出来的数字不再抄一份，避免两份数据打架
- 没有数据的日期**补 0**：否则趋势图会把「那天没人看」画成「那天不存在」

## 十一、收银台（POS 开单）

用户诉求：「有的客户需要这种收银台类似的客户端」。

**为什么很轻**：商品/SKU、成品库存、出库台账、应收账款、收付款中心、客户档案都已存在，
缺的只是「一屏完成选货 → 改价 → 收款」的单据。

- 数据模型 `V202710100004`：`t_pos_sale` + `t_pos_sale_item`（明细冗余款号/款名/颜色/尺码，
  是成交当时的**快照**：之后改名或删 SKU，小票与对账仍要能还原当时卖了什么）
- 出库**复用既有 `freeOutbound`**（扣库存 + 落台账），与店铺订单同一正路
- 收款方式只**登记**（现金/微信/支付宝/刷卡/挂账），不接真实支付通道 —— 零牌照风险、立刻能用
- **挂账才生成应收**（进既有收付款中心核销）；当场收款不生成应收，
  否则同一笔钱会在「已收款」与「应收未收」里各出现一次
- 批发场景三件：**客户历史价**（输手机号带出上次成交价）、整单折扣/抹零、挂账生成应收
- 前端：PC 网页版全屏收银台（扫码枪就是键盘，回车即加一件，精确命中排最前）
- 权限：顶层菜单 `MENU_POS` + 登录态（动库存与应收，绝不能像 C 端店铺页那样免登录）

## 十二、后续（仍需先定策略）

- **商品审核**（是否所有租户都要审）——会改变租户「上架即生效」的既有习惯
- 类目树维护（当前只有一份扁平中文词表）
- 看板的趋势图/转化归因（需要更细的埋点与口径定义）
- 收银台的真实支付通道、小票打印、交班对账（当前只做登记与汇总）
- 若日后改主意要抽佣，才需要平台代收/分账（当前明确不做）
