# 平台级电商 · P0 设计与落地说明

> 决策前提（2026-10-09 用户拍板）：**资金各租户直收，平台不抽成**（走方案 B）。
> 平台只做「公共商城 + 引流 + 账号」，不碰钱、不做分账。

## 一、P0 要解决什么

把 D-763 的「每租户一个独立小店」升级为**平台方运营的公共商城**：

| 维度 | P0 之前（D-763） | P0 之后 |
|---|---|---|
| 入口 | `/shop/index.html?s={slug}`，一租户一店 | 新增 `/shop/platform.html` 平台首页（跨店商品池），店铺页降级为「平台里的一家店」 |
| 身份 | 免登录，手机号即身份 | **平台级 C 端账号**（手机号 + 密码，一人一号、跨店通用），与免登录**并存** |
| 商品 | 只查本租户 `shop_listed=1` | **跨租户商品池**（搜索 / 类目 / 店铺维度） |
| 收货地址 | `t_shop_address`（租户 + 手机号） | 新增 `t_shop_consumer_address`（平台级，跨店复用）；旧表保留不动 |
| 订单 | 一单只含一个租户 | 不变（一单仍只含一个店铺 —— 资金各店直收的必然结果） |
| 平台方 | 无 | 只读总览：店铺 / 在架商品 / 注册用户 / 订单计数 + 最近订单 |

## 二、数据模型（迁移 `V202710090002__create_platform_shop_consumer.sql`）

- `t_shop_consumer`：平台级 C 端账号（**无 tenant_id**，手机号全局唯一）
- `t_shop_consumer_address`：平台级收货地址簿（**无 tenant_id**）
- `t_shop_order.consumer_id`：登录用户下单时写入，支撑「我的订单（跨店）」

两张新表**刻意不带 tenant_id**，并已在 `TenantInterceptor.EXCLUDED_TABLES` 登记为全局表
（否则带租户上下文查询会拼出 `AND tenant_id = X`，而该列并不存在 → SQL 报错）。
`scripts/audit-tenant-id.py` 的豁免清单也同步登记了 `ShopConsumer*`。

## 三、身份与令牌（关键安全设计）

消费者令牌与员工令牌是**两套身份**：

1. 消费者令牌走独立请求头 `X-Shop-Token`，`TokenAuthFilter` 根本不读它；
2. 令牌内 `roleName = shop_consumer`，且 `TokenAuthFilter` **显式拒绝**该角色 ——
   即使有人把消费者令牌塞进 `Authorization`，也拿不到「已登录员工」身份。
   （判据常量放在 `SecurityConstants.SHOP_CONSUMER_ROLE`，避免 auth → shop 反向包依赖。）
3. 令牌有效期 30 天，无刷新令牌（C 端无资金操作，体验优先）。

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/shop/public/auth/register` | 注册（手机号 + 密码 + 可选昵称）→ 直接返回令牌 |
| POST | `/api/shop/public/auth/login` | 登录 |
| GET | `/api/shop/public/me` | 个人资料 |
| POST | `/api/shop/public/me` | 改昵称 / 头像 |
| GET/POST | `/api/shop/public/me/addresses` | 平台级地址簿（跨店复用） |
| POST | `/api/shop/public/me/addresses/{id}/default` `/delete` | 设默认 / 删除 |
| GET | `/api/shop/public/me/orders` | **我的订单（跨店）** |

| 方法 | 路径 | 说明 |
|---|---|---|

## 五、跨租户只读查询

`ShopPlatformMapper` 类级 `@InterceptorIgnore(tenantLine = "true")` 绕过租户拦截器
（与 `IntelligenceProcessStatsMapper` 同一做法），只提供 SELECT，且不含成本/供应商等内部字段。

## 六、刻意**不做**的事（避免越界返工）

- ❌ 平台代收 / 分账 / 佣金：用户已明确「资金各租户直收，平台不抽成」
- ❌ 跨店购物车 / 拆单：一单仍只含一个店铺
- ❌ 平台运营后台的**写**能力（商品审核、类目管理）：留待 P2，权限边界定型后再开
- ❌ 短信验证码登录：`SmsLoginHelper` 已具备能力，但未开通短信网关时不可用，故 P0 用密码登录

## 七、P1（本轮已实现）：跨店购物车 + 结算拆单 + 订单详情

| 能力 | 实现 |
|---|---|
| 跨店购物车 | `t_shop_cart_item`（**挂在 consumer_id** 下，`(consumer_id, sku_id)` 唯一；`tenant_id` 只作结算分组键） |
| 加购 | 服务端校验：SKU 存在 / 款式在架 / 库存充足；同 SKU **累加**而非插两行 |
| 失效商品 | 下架 / 打烊 / 缺货的行**照常返回**并带 `available=false` + 可读原因，绝不静默消失 |
| 结算 | `POST /api/shop/public/me/checkout` —— **按店铺逐张下单**，一张订单只含一个店铺 |
| 失败隔离 | 每店独立事务；某店失败**不影响其他店**，失败店铺的商品**留在购物车**待重试 |
| 订单详情 | `GET /api/shop/public/me/orders/{orderNo}` —— 明细 + 物流 + 售后状态，**必须同时匹配 consumerId** |

接口一览（均在 `/api/shop/public/me/**`，身份走 `X-Shop-Token`）：

- `GET /me/cart`、`POST /me/cart`、`POST /me/cart/{id}/quantity`、`POST /me/cart/{id}/delete`、`POST /me/cart/clear`
- `POST /me/checkout`（body：`customerName / phone / address / remark / tenantIds`）
- `GET /me/orders/{orderNo}`

## 八、P2（本轮已实现）：买家售后 + 商品评价

### 8.1 买家售后（补上闭环断裂的那一半）

此前售后只有**商家代顾客登记**的入口（`ShopAdminController` 的 after-sale/apply）——
顾客收到有问题的货，在系统里无处发起，只能打电话，商家再手动登记。
状态机（`APPLIED → APPROVED/REJECTED`）早就有了，缺的是「APPLIED 由谁触发」。

- `POST /api/shop/public/me/orders/{orderNo}/after-sale`（body：`type` / `reason`）
- 只有**已发货**订单可申请（未发货提示走取消订单）；`APPLIED`/`APPROVED` 时不可重复申请，
  `REJECTED` 后允许再申请
- 审批仍走商家侧既有逻辑，**不重复实现**库存回补与应收冲销

### 8.2 商品评价

- 表 `t_shop_review`：粒度 **一单一款一条**（`order_id + style_no` 唯一）；
  带 `tenant_id`（商家查自己店铺评价仍走租户隔离）
- 规则：只有已发货订单可评价；款式必须在该订单里；星级 1~5；内容 ≤ 500 字；
  **提交后不可修改**（防刷分）
- `POST /api/shop/public/me/orders/{orderNo}/reviews`
- `GET /api/shop/public/platform/styles/{styleId}/reviews` —— 公开可读的均分 + 条数 + 最新评价
- 商品池卡片展示 `★4.5 (12)`；平台商品弹层展示最新评价；订单详情里逐款评价 / 显示「已评价」
