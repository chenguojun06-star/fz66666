## 核实 1：EOL 日期 ✅ 已用官方原文验证

### 官方政策原文（spring.io/support-policy）

> "Spring Boot releases will be supported for **13 months** from the date such release
> was made available for download, **rounded to the end of the month**."
> "For example, if Spring Boot 2.7.0 was released on 2022-05-19, open source support
> will extend to 2023-06-30."

### 按规则逐条推算

| 版本 | GA 日期 | +13 个月 → 月末 | 结论 |
|---|---|---|---|
| Boot 3.4.0 | 2024-11-21 | **2025-12-31** | ✅ 与我原文档一致 |
| Boot 3.5.0 | 2025-05-22 | **2026-06-30** | ✅ 与我原文档一致 |
| Boot 4.0.0 | 2025-11-20 | **2026-12-31** | ✅ 一致 |
| Boot 4.1.0 | 2026-06-10 | **2027-07-31** | ✅ 一致 |

### 佐证：Spring Boot 3.5.16 官方博客（2026-06-25）原文

> "This is the **last OSS release of the 3.5.x generation**.
> To continue to receive OSS support, upgrade to 4.0.x or 4.1.x"

### ⚠️ 核实结论修正了一处我的错误

原文档「五、建议排期」写：

> **步骤 1：3.4.5 → 3.5.x（低风险，可立即做）** … 收益：离开 EOL 状态

**这条建议是错的。** 3.5 的 OSS 支持也在 **2026-06-30 结束**（已过 3 个月），
升到 3.5.x 只能买到 **到年底的窗口**，不是稳定落点。

**修正后的落点只有两个选项：**

| 方案 | 说明 |
|---|---|
| **A. 维持现状 + 商业支持** | Boot 3.5 的 enterprise support 可至 2032（官方政策：最后 minor 额外 +5 年），需采购 |
| **B. 直接目标 4.1.x** | 跳过 3.5 缓冲，⚠️ Jackson + Security 风险叠加 |

**不存在"低风险先升 3.5"这条中间路线** —— 这是本次核实纠正的最大认知错误。

## 核实 3：Jackson 实际改动量 ✅ 已实测（原为估算，现为分类计数）

原文档写「245 个文件 / 650 处」，但**没分类**。实测分类：

| 类别 | 文件数 | 迁移难度 |
|---|---|---|
| ① 仅用 `@JsonProperty`/`@JsonFormat` 等注解 | **40** | 🟢 低（改 import） |
| ② 使用 `ObjectMapper` | **207** | 🟡 中（Jackson 3 改名 `JsonMapper`） |
| ③ 使用 `TypeReference` | **93** | 🟡 中（包路径变化） |
| ④ 使用 `JsonNode` | **46** | 🟢 低（API 基本兼容） |
| ⑤ 使用 `readValue`/`writeValueAsString` | **206** | 🟡 中（核心 API） |

### 🔑 关键发现：Jackson 2 与 Jackson 3 是不同 groupId，**可以共存**

```
当前：com.fasterxml.jackson.*  (groupId com.fasterxml.jackson.core)
Jackson 3：tools.jackson.*     (groupId tools.jackson.core)
```

**含义：Boot 4 不强制迁移到 Jackson 3。** 若代码不主动改依赖，会继续用 Jackson 2，
那 **245 个文件一个都不用改**。

**所以 Jackson 的真实工作量取决于一个决策，而非技术必然：**

| 选项 | 工作量 | 风险 |
|---|---|---|
| **不迁**，继续用 Jackson 2 | **0 文件** | 🟢 最低。Jackson 2 仍独立维护，不受 Boot 4 影响 |
| 迁到 Jackson 3 | 245 文件 | 🔴 高，且触发下方核实 4 的序列化行为变更 |

**建议：不迁。** 除非有明确需求要用 Jackson 3 特性。
这样步骤「升级 Boot」的代码改动可能远低于原文档估计。

## 核实 4：序列化契约风险 ✅ 已实测

原文档提出「Jackson 3 默认改字段顺序」的担忧。实测敞口：

| 检查项 | 结果 | 判断 |
|---|---|---|
| 前端按字段顺序索引（`Object.values()[0]`） | **0 处** | 🟢 无风险 |
| `@JsonPropertyOrder` 显式声明顺序 | **0 处** | 🟢 无 |
| 后端 JSON 签名逻辑文件 | 30 个 | 🟡 需逐个确认 |

### 🔑 关键发现：电商签名与 Jackson 顺序无关

`SignatureUtils.buildSortedSign()` 用 **`TreeMap`** 排序参数后拼接：

```java
java.util.TreeMap<String, Object> sorted = new java.util.TreeMap<>(params);
```

→ **签名内容与序列化顺序无关**，Jackson 迁移不影响淘宝/京东/拼多多签名。
（也正因此，CLAUDE.md 铁律 2 强调"用 `buildSortedSign` 不要自己写"是对的。）

### ⚠️ 唯一真实敏感点：微信支付 v3 回调验签

```java
buildWechatV3CallbackMessage(timestamp, nonce, body)
buildWechatV3SignMessage(httpMethod, url, timestamp, nonceStr, body)
```

**签名的是「原始 HTTP body 字符串」**，字节级敏感。
但该 body 是**从 HTTP 请求读入的原始字符串**，不是 Jackson 序列化产物
→ **Jackson 迁移不影响它**。

### 结论

| 风险 | 状态 |
|---|---|
| 前端字段顺序依赖 | 🟢 无（0 处） |
| 电商三方签名 | 🟢 无（TreeMap 排序，与序列化无关） |
| 微信 v3 回调验签 | 🟢 无（签原始 body，非序列化产物） |

**「序列化契约」风险在本次核实后被排除。** 原文档把它列为"⚠️ 建议补 JSON 快照测试"
属于过度谨慎 —— 前提是「迁 Jackson 3」，而核实 3 的结论是**建议不迁**。

## 核实 5：Spring Security 7 影响面 ✅ 已实测（比预估小得多）

原文档估「186 文件」显得吓人。实测 API 分布：

| API | 文件数 |
|---|---|
| `@PreAuthorize` | **185** |
| `PasswordEncoder` | 15 |
| `Jwt` 相关 | 9 |
| `BCryptPasswordEncoder` | 2 |
| `requestMatchers` / `antMatchers` | 2 |
| `SecurityFilterChain` | **1** |
| `authorizeHttpRequests` | 1 |
| `@EnableMethodSecurity` | 1 |
| `WebSecurityConfigurerAdapter`（已废弃） | **0** ✅ |
| `@Secured` / `@PostAuthorize` | 0 |

### 关键判断

**185 处 `@PreAuthorize` 不构成 Security 7 升级风险**——它是方法级注解，
在 `SecurityConfig`（**仅 1 个文件**）启用 `@EnableMethodSecurity` 后由框架处理，
升级不会要求改这 185 处。

真正的回归面是 **1 个 `SecurityConfig` + `TokenAuthFilter` + 15 处 PasswordEncoder**。

## 综合结论：核实后风险显著下降

| 项 | 原文档评估 | 核实后 |
|---|---|---|
| Jackson | 🔴 245 文件 | 🟢 **0 文件**（建议不迁 Jackson 3） |
| Security | 🟡 186 文件 | 🟢 **约 20 文件**（配置集中） |
| 序列化契约 | ⚠️ 需补快照测试 | 🟢 **风险排除**（实测无敞口） |
| 步骤 1（先升 3.5） | 🟢 低风险建议 | ❌ **建议错误，已撤销** |

### ⚠️ 但仍有一个硬约束没变

**Boot 与 Spring AI 版本绑定，且 3.5 也是 EOL —— 没有"低风险中间落点"。**

剩下的选择只有：
- **A**：维持现状，采购 enterprise support（Boot 3.5 可支持至 2032）
- **B**：接受风险，一次性上 4.1.x

### 仍未实测的项（本次核实范围外）

1. **MyBatis-Plus 3.5.17 与 Boot 4.1.1 的实际兼容性**（其传递依赖钉在 4.0.1）
2. **Spring AI 1.0 → 2.0 的 API 破坏性变更对 57 个 `ChatClient`/`Advisor` 使用文件的影响**
   （2.0 把工具调用循环从各 ChatModel 私有实现提到 Advisor 链，是大改）
3. **2332 个 Java 文件在 Boot 4 下的实际编译结果**（含 Tomcat 11、Security 7 的连带变更）

> 这三项**必须通过实际升级分支验证**，无法靠文档推断。
