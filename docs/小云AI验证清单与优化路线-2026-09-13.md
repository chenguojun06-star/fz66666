## 第一步 · 5 分钟快速验证（最优先，做完再谈优化）

今天上线的 6 项行为变化**全部未验证**。下面 10 个问题，对着小云问一遍，
每条的"看什么"决定了这项改动是否真的生效。

### A. 验证技术改动是否生效（看后端日志）

| # | 问什么 | 看什么（日志关键词） | 说明 |
|---|---|---|---|
| 1 | 有哪些订单可能会延期 | `[Rerank] provider=... candidates=N topN=M → K 条` | **最关键**。candidates 应该 >5（说明 top-k 20 生效），且有 rerank 耗时 |
| 2 | 这个月一共生产了多少件 | `precheck` / `retried=` / `elapsedMs=` | Text-to-SQL 预校验与耗时是否打出来了 |
| 3 | （接上题，故意问个模糊的） | `SQL 预校验未通过，已阻止执行` | 预校验能否拦住错误 SQL |
| 4 | 今天有多少订单在生产 | `[GroundingGuard] 数值声明无依据` | 若出现，看 `claim=` / `normalized=` / `evidenceNumbers=` 是否合理 |
| 5 | （触发一个 SOP 场景） | `[ProceduralMemory] 检索SOP ... keyword=` | 关键词是否像人话，而不是"前10个字符" |
| 6 | 触发一次 schema 重灌 | `[StyleVectorBackfill]` 批次日志 | 批量写入是否生效（批次而非逐条） |

### B. 验证业务效果（你自己能判断对错）

| # | 问什么 | 判断标准 |
|---|---|---|
| 7 | `HYY202601111` 这个款现在什么进度 | 返回正确进度，不是"没找到"（**A 组精确检索，今天优化的重点**） |
| 8 | 有哪些订单可能会延期 | 列出具体订单 + 原因，不是泛泛而谈 |
| 9 | 各工厂的订单量排名 | 返回真实排名数据，SQL 没报错 |
| 10 | 款号 `ZZZ999999999` 的进度 | **明确说没有**，不是编一个答案 |

> ⚠️ 第 7 条要把款号换成你库里真实存在的，否则测的是"拒答"不是"检索"。

**如果这 10 条里 1、7、9 有问题** → 说明今天的改动有回归，先定位再继续。
**如果都正常** → 进入第二步。

## 第二步 · 激活混合检索（代码已就位，等你操作）

这是**今天唯一"代码全做完但还没生效"**的功能。混合检索能让款号/色号/订单号
这类精确编码的检索能力上一个台阶 —— 而这正是服装业务的刚需。

### 操作步骤

```bash
# ① 建新集合（命名向量模式）
#    CloudBase 控制台加环境变量：
QDRANT_COLLECTION_NAME=fashion_memory_v2
QDRANT_NAMED_VECTORS=true
#    → 重启 backend

# ② 触发重灌（约 100~300 次 embedding 调用，批量写入后几分钟内完成）
curl -X POST https://<host>/api/intelligence/qdrant/backfill-sparse-vectors \
  -H "Authorization: Bearer <你的token>"

# 查进度（stage 走到 DONE 即完成）
curl https://<host>/api/intelligence/qdrant/backfill-sparse-vectors/progress

# ③ 可选：开 sparse-v2（去中文单字符噪声 + 哈希扩到 31 位）
#    → 重启

# ④ 重跑第一步的第 7 条（款号检索），对比效果
```

### 出问题怎么退

```bash
QDRANT_COLLECTION_NAME 改回旧值（或删掉）
QDRANT_NAMED_VECTORS=false
# → 重启即回退，旧集合全程没被动过
```

## 第三步 · 按需优化（4 项，都带触发条件）

**不要一次全做。** 每项都有明确的"什么时候才值得做"。

| 优先级 | 项 | 什么时候做 | 预计收益 |
|---|---|---|---|
| 1 | schema 向量独立 collection | 如果发现"问业务问题却召回了表结构" | 降检索噪声 |
| 2 | Query 改写并行化 | 如果实测多轮对话延迟 >3 秒 | 省几百毫秒 |
| 3 | 真流式输出 | 如果用户抱怨"等半天才出字" | 首字延迟大幅下降 |
| 4 | AutoLink 渐进 schema linking | 如果 Text-to-SQL 召回表 >15 张 | SQL 准确率 |

**第 3 项注意**：并行会话正在改流式（`StreamingAgentLoopCallback` / `useAiChatStream.ts`），
要动的话先跟对方对齐，别撞车。

## 第四步 · 数据驱动（什么时候该考虑换模型）

**关键判断**：如果第一步验证后出现下面这个组合，瓶颈就不在检索层了：

```
检索指标正常（能召回正确内容）+ 答案质量仍然不满意
→ 瓶颈在模型层
```

**当前用的是 `deepseek-flash`（轻量档）。** 如果多步推理、复杂统计类问题表现吃力，
换更强的模型比继续优化检索更划算 —— 而且换模型是**改配置的事**，不动代码。

**所以：先别动。等第一步数据出来再判断。**

---

## 一个必须记住的原则

> **优化不是清零，是收敛。**

判断标准就三条：
1. 核心指标没退步（第一步 10 条）
2. 没有已知的 P0 缺陷（目前只剩 Text-to-SQL 用 root 数据源，是独立安全项）
3. 延迟用户能忍

**三条都满足就该停**，剩下的交给监控数据驱动 ——
哪个功能抱怨多、哪个查询慢，再针对性优化。
比现在凭代码审查猜"哪里可能有问题"靠谱得多。
