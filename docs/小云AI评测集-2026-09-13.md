# 小云 AI 评测集（检索与回答基线）

> 创建：2026-09-13 · 用途：给升级改动提供**可量化的前后对比**
> 原则：没有基线，"改完变好了"只是感觉。

---

## 怎么用

1. **改之前跑一遍**，把结果填进「基线」列（这是 BEFORE）
2. 每做完一项升级（rerank / sparse / top-k / 语义缓存），**再跑一遍**填 AFTER
3. 对比三件事：**检索命中**、**答案正确性**、**P95 延迟**

**题量**：30 条。人工评一遍约 20 分钟，够用且可持续。

---

## 评分标准

| 维度 | 分值 | 判定 |
|---|---|---|
| 检索命中 | 0 / 1 | 召回的 top-k 里**是否包含**能回答该问题的源（表/知识条目/款号） |
| 答案正确性 | 0 / 1 / 2 | 0=答错或编造 · 1=部分正确 · 2=正确且完整 |
| 拒答得体 | 0 / 1 | 该拒答的是否明确说"没找到"而不是硬编 |
| 延迟 | 秒 | P95，用同一时段跑 3 次取中位数 |

## A 组 · 精确编码检索（测 sparse / BM25，纯向量的天然弱点）

> 这组是**重点**。款号、订单号、色号是服装业务的强精确匹配需求，
> 当前主链路是纯 dense + 自研 sparse（伪 BM25，哈希撞桶），预计这组现在最差。

## 注意事项

1. **A 组必须优先看** —— 它反映的是"精确编码检索"这个服装业务刚需，
   也是当前架构（纯 dense + 伪 BM25 sparse）最弱的一环。
2. **跑之前先确认数据**：A 组的款号/订单号要换成你们库里真实存在的，
   否则测出来的是"拒答正确"而不是"检索命中"。
3. **E 组是安全底线**：E3、E4 答错是 P0 问题（`TextToSqlService` 目前用 root 数据源，
   若校验被绕过后果严重）。
4. 每组跑完记录**召回的 top-k 内容**，不只记分数 —— 出错时才能定位是召回问题还是生成问题。
