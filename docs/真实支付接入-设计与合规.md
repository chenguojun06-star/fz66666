# 真实支付接入（微信支付 / 支付宝）· 设计与合规说明

> 面向：需要开通在线收款的商家、以及维护这套代码的同学。
> 一句话结论：**在线收款用的是商家自己的商户号，钱直接进商家账户，平台不经手资金。**

---

## 一、先讲红线：为什么不能"平台一个商户号收所有商家的钱"

微信支付/支付宝的**商户号是企业资质**，资金结算到该企业绑定的银行账户。

如果平台用自己的商户号收所有商家的钱、事后再转付给商家，这叫**二次清算（二清）**：
无《支付业务许可证》从事支付结算属**非法经营**，同时平台还要承担资金池风险、
税务风险与商家跑路/平台挪用的信任风险。

所以只有一种合规做法：

```
商家A ── 自己的商户号A ──► 商家A 的银行账户
商家B ── 自己的商户号B ──► 商家B 的银行账户
平台：只提供技术通道（下单、回调、对账），不碰钱、不做资金池
```

这也与产品既定方向一致：**各租户直收、平台不抽成**。

> 代价要说清楚：每个商家需要自己去申请商户号（营业执照、法人身份证、银行账户），
> 微信/支付宝审核通常几个工作日到两周；还要准备**已备案的域名**用于接收异步通知。
> 这些是外部资质，系统无法代劳，但**配置入口已经做好，拿到参数填进去即可收款**。

## 二、数据模型

### 2.1 `t_payment_config`（每租户收款配置）

| 列 | 说明 |
|---|---|
| `tenant_id` + `channel` | 唯一键 `uk_tenant_channel`：一个租户每个渠道一条 |
| `enabled` | 启用开关（启用且参数齐全才允许发起支付） |
| `app_id` / `mch_id` / `serial_no` | 非敏感标识 |
| `private_key_cipher` / `public_key_cipher` / `api_v3_key_cipher` | **AES-256-GCM 密文** |
| `notify_url` | 异步通知地址（须公网可达、域名已备案） |
| `gateway_url` / `sandbox` | 支付宝可指向沙箱 |

**密钥安全**：
- 明文只存在于"发起支付/验签"的那一瞬间，落库前用 `AesEncryptor` 加密（主密钥来自
  `APP_SECURITY_PII_ENCRYPTION_KEY`）；
- 接口**绝不回传密钥**，只返回"是否已设置"；要改就整段重填；
- 密钥字段留空 = 保持原值，传 `-` = 清空（改个回调地址不会把私钥弄丢）；
- 换了加密主密钥导致解不开时，表现为"该渠道不可用、请重新填写"，而不是整条链路 500。

### 2.2 `t_payment_record`（支付流水，复用既有集成跟踪表）

一条业务单（如 POS 销售单）对应一条流水，状态机：

```
PENDING ──支付成功──► SUCCESS ──退款──► REFUNDED
   └────超时/取消──► CANCELLED
```

**幂等的实现**：状态跃迁一律走条件更新

```sql
UPDATE t_payment_record SET status='SUCCESS', ...
 WHERE tenant_id=? AND order_id=? AND channel=? AND status='PENDING'
```

影响行数 = 1 才说明"本次调用完成了跃迁"，此时才执行下游业务落账；
= 0 表示重复回调 → 直接跳过。**这是防重复出库/重复记账的唯一依据。**

### 2.3 `t_pos_sale` 新增

- `channel_trade_no`：渠道交易号（微信 `transaction_id` / 支付宝 `trade_no`），对账用
- `paid_time`：实际收款时间
- `pay_status` 增加 `PAYING`（待支付）与 `CANCELLED`（已取消）

## 三、支付流程

### 3.1 收银台（主扫：顾客扫屏幕上的二维码）

```
收银员选货 → 点"微信/支付宝" → 服务端算价、落销售单(PAYING，不出库)
        → 向渠道下单拿二维码 → 收银台展示二维码 + 倒计时
        → 顾客扫码付款
        → 渠道异步回调（验签） 或 收银台轮询 pay-state（服务端主动查渠道）
        → 确认收款（幂等）→ 出库 + 落台账 → 单据置 PAID → 计入今日收款
```

**关键设计**：
- **待支付不出库**：只有"钱到位"才出库（现金/刷卡当场、挂账记账、在线等渠道确认）。
  否则顾客不付钱，货已经出去了。
- **回调 + 主动查询双通道**：回调可能丢（网络、发布重启、地址配错），
  所以收银台每 2 秒轮询一次 `pay-state`，服务端会**主动向渠道查询**并就地确认。
- **取消要双向**：先向渠道查询确认"确实还没付"，再关渠道单，最后本地置 CANCELLED；
  已支付成功的单不允许取消（只能走退款）。
- **实付 < 应收 → 拒绝出库**：宁可让人工核对，也不能按低价发货。
- **已取消却收到钱 → 抛错**：钱在渠道账上，必须人工核对后走退款，绝不悄悄出库。

### 3.2 回调地址

| 渠道 | 地址 | 为什么这样 |
|---|---|---|
| 支付宝 | `/api/webhook/payment/alipay` | 回调是明文，用 `app_id`（全局唯一）反查租户与公钥 |
| 微信支付 | `/api/webhook/payment/wechat/{tenantId}` | 回调 body 加密，解密需要该商户的 APIv3 密钥，**没法先解析单号再反查租户**，所以地址带 tenantId |

**验签与拒绝策略**（历史实现踩过的坑，现在写成硬规则）：

1. 未配置渠道 → **直接拒绝**，不解析、不落账；
2. 验签失败 → 拒绝（返回 fail 让渠道按策略重推）；
3. 验签通过但流水不存在 → 不落账，**打错误日志**提示核对渠道账单；
4. 重复推送 → 幂等跳过，但仍回 success（否则渠道会一直重推）；
5. 微信侧还额外校验解密出来的 `mchid` 与配置一致，防止别人拿自己的商户号往我们这推。

> ⚠️ 历史版本里 `verifyCallback` 在"密钥未配置"时**直接返回 true**，
> 等于任何人都能 POST 一个 `trade_status=TRADE_SUCCESS` 把单刷成已支付。
> 这条已被 `PaymentSchemaGuardTest` 守住。

## 四、商家怎么开通（操作步骤）

1. **申请商户号**
   - 微信支付：<https://pay.weixin.qq.com> → 提交营业执照等资质 → 开通「Native 支付」
   - 支付宝：<https://open.alipay.com> → 创建应用 → 签约「当面付」
2. **拿密钥**
   - 微信：商户平台 → 账户中心 → API 安全 → 申请 API 证书（拿 `apiclient_key.pem` 与证书序列号）→ 设置 APIv3 密钥
   - 支付宝：开放平台 → 密钥工具生成 RSA2 应用私钥 → 上传公钥 → 复制「支付宝公钥」
3. **配回调地址**：把系统「店铺管理 → 收款设置」页面上给出的回调地址，原样填到商户平台。
   域名必须**已备案且公网可达**；填错会导致"顾客付了钱、系统还是待支付"。
4. **在系统里填写**：店铺管理 → 收款设置 → 粘贴参数 → 打开"启用" → 点「连通性验证」。
5. 验证通过后，收银台的微信/支付宝按钮自动变为可点。

> 「连通性验证」的做法：拿一个必然不存在的单号去查询渠道 ——
> 密钥不对会报签名错误（验证失败）；密钥正确会报"订单不存在"（说明鉴权通过）。
> **不产生任何资金动作。**

## 五、代码结构

```
integration/payment/
├── PaymentGateway.java             统一接口（每个方法都接收"已解密的租户配置"）
├── PaymentManager.java             按租户取配置 + 分发（未配置一律拒绝）
├── PaymentBusinessHandler.java     业务侧接口（POS 实现它，支付模块不反向依赖业务）
├── config/
│   ├── PaymentConfig.java          落库实体（密钥是密文）
│   ├── PaymentChannelConfig.java   运行态（含明文密钥，用完即弃）
│   ├── PaymentConfigMapper.java
│   └── PaymentConfigService.java   读（解密）/写（加密）/状态展示
├── channel/
│   ├── RsaSignUtil.java            RSA2 签名/验签（JDK 自带，不引新依赖）
│   ├── AlipayGatewayClient.java    支付宝协议（预下单/查询/关单/退款/回调验签）
│   └── WechatPayGatewayClient.java 微信 V3（用官方 SDK）
├── impl/
│   ├── AlipayAdapter.java          协议编排，无 Mock 分支
│   └── WechatPayAdapter.java
├── orchestration/
│   ├── PaymentOrchestrator.java    发起/查询/关单
│   ├── PaymentConfirmOrchestrator.java  钱到账的唯一入口（幂等）
│   ├── PaymentCallbackOrchestrator.java 回调验签→解析→确认
│   └── PaymentConfigOrchestrator.java   收款设置
├── controller/PaymentConfigController.java
└── callback/PaymentCallbackController.java
```

POS 侧：

```
pos/orchestration/PosSaleOrchestrator.java  开单编排（在线支付只发二维码，不出库）
pos/service/PosSaleWriteService.java        事务内写操作（落单 / 出库结算 / 取消）
pos/orchestration/PosPaymentHandler.java    实现 PaymentBusinessHandler
```

**为什么把写操作单独放到 `PosSaleWriteService`**：在线支付要在中间调渠道 HTTP 接口，
如果把"插销售单"和"调渠道接口"放同一个事务里，数据库连接会在外部调用期间一直被占着，
收银高峰期容易把连接池拖干。拆成 `createSale（事务）→ 调渠道（无事务）→ settle（事务）`，
顺带让"发起支付失败 → 作废单据"这个补偿动作变得显式可读。

## 六、测试覆盖（哪些能自动验证、哪些不能）

**能真实验证的（已覆盖）**：
- RSA2 签名/验签闭环（现场生成密钥对，篡改内容必须验不过）
- 待签名串拼法（排序/排除 sign/跳过空值/值不 URL 编码）
- 分 ↔ 元换算（含来回换算不丢精度）
- 回调验签拒绝策略（无 sign / 无公钥 / 篡改金额 / 篡改单号）
- 密钥加密落库、留空保持原值、`-` 清空、启用前完整性校验
- 幂等：重复回调不重复落账
- 收银台：待支付不出库、实付不足拒绝出库、取消双向、交班只统计已到位
- 结构守护（`PaymentSchemaGuardTest`）：8 条"改回去就出事"的硬规则

**无法自动验证、必须拿到真实商户号才能跑的**：
- 真实下单/扫码/回调联调（需要商户号 + 已备案域名）
- 微信平台证书自动下载（需要真实商户私钥）
- 退款到账

**建议的联调顺序**：先用支付宝**沙箱**（`sandbox=true`）跑通下单与回调，
再上微信；两边都通了再开正式环境的启用开关。
