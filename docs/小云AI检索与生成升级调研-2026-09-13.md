## 一、现状盘点（精确基线）

### 1.1 检索链路：主路径其实是纯 dense

| 环节 | 实现 | 位置 |
|---|---|---|
| 主 RAG 入口 | `PromptContextProvider:319 buildRagContext` → `AgenticRagService:209 retrieve` | — |
| 自我修正 | 最多 3 轮：第 1 轮规则改写、第 2 轮起 LLM 改写（`rewriteQueryWithLlm:391`） | `AgenticRagService` |
| 底层检索 | **纯 dense**：只传 vector + limit + `score_threshold=0.3` + tenant 过滤 | `QdrantService:310` |
| 混合检索 | `hybridSearch:406`（dense+sparse）**只被 `AgenticRagService:744` 调用** | 非主路径 |
| 工具检索 | dense(topK=10) + SQL LIKE(10) + 知识图谱(3) → RRF 融合 | `KnowledgeSearchTool:227` |
| **Rerank** | `CohereRerankService` 代码存在并在 `KnowledgeSearchTool:248` 调用，<br>但 `application.yml:417 ai.cohere.rerank.enabled: false` → **生产没生效** | ⚠️ 关键 |
| 召回量 | `recall-top-k: 3`（`application-prod.yml:169`），阈值 0.45 | 偏小 |
| HyDE / 多查询扩展 | **无** | — |

**⚠️ 三个必须纠正的认知**：
1. **混合检索不是主链路能力** —— 日常 RAG 走的是纯 dense，sparse 只在工具和 `AgenticRagService:744` 用。
2. **Rerank 不是"没有"，是"写了但关着"** —— 已有 `CohereRerankService` 集成，只需换 provider + 开开关。
3. **`CragEvaluator` 是孤岛** —— 唯一消费方是 `SafeAdvisorOrchestrator:71`（`/safe-advisor/analyze`），
   **不在主 Agent 链路上**。别把它算作现有资产，也别基于它做规划。

### 1.2 稀疏向量：自研「伪 BM25」

```java
int tokenId = Math.abs(entry.getKey().hashCode()) % 100000 + 1;  // ① 哈希冲突
float tf = (float) entry.getValue() / maxFreq;                    // ② 只有 TF，无 IDF
```
- ① **10 万桶装中文 bigram** → 语义无关词撞桶 → 错误匹配。服装场景的款号/色号/尺码一旦撞桶，精确检索失效。
- ② **无 IDF** → "的"、"生产"、"订单"这类高频词与稀有专业词权重相同，区分度被稀释。
- ③ 中文**单字符也建索引** → 纯噪声。

### 1.3 记忆系统

| 组件 | 实现 | 短板 |
|---|---|---|
| `ProceduralMemoryService` | L4 SOP，MySQL + Qdrant 双写；`trigger_keywords LIKE` → 语义兜底(topK=10, confidence≥0.60) | `extractKeyword:160` 是 **13 个硬编码词 + 兜底取前 10 字符**；无衰减，只有 usage/success 计数 |
| `SharedAgentMemoryService` | 同会话 Sub-Agent 共享事实，纯 MySQL 不进 Qdrant；滑动续期 24h、硬上限 7 天 | `readFact:124` **先全量拉会话再 filter** |
| 衰减 | `IntelligenceMemoryOrchestrator:223` 半衰期 90 天；`LongTermMemoryOrchestrator:243` 衰减 40% + BM25 30% + 实体 30% | 衰减逻辑分散在两处 |

### 1.4 Text-to-SQL

- `SchemaVectorManager:144 searchRelevantTables`：关键词打分（表名50/注释40/字段15-20）+ Qdrant 检索
- **⚠️ schema 向量与记忆向量混在同一个 collection（`fashion_memory`）**，靠 `schema_` 前缀过滤 → 噪声大
- `MAX_TABLES_FOR_CONTEXT=6`，字段 25/表，上下文上限 3000 字符
- few-shot **只有 prompt 里 1 个静态示例**（`:289`），无动态检索
- **无 SQL 预校验、无执行失败重试**（extractSql → 直接执行，出错就返回）
- `SqlSecurityValidator`：关键字黑名单 + 拒绝 UNION 与所有子查询 + PII 字段黑名单 + 500 行/15s
- **🔴 `TextToSqlService:32-52` 自认用主数据源 root JdbcTemplate —— 已记录未修的 P0 安全风险**

### 1.5 生成与模型

- 模型：`deepseek-flash`（`spring-ai` adapter）
- **temperature 配置不一致**：`application.yml:385` 是 0.7/1024，`SpringAiAdapterConfig:44` 另有一套 0.3/2048
- Embedding：硅基流动 `BAAI/bge-m3`，1024 维
- **Streaming 名不副实**：`SpringAiInferenceAdapter:148 chatStream` 用 `.blockLast()` 阻塞收集后再推 SSE
- `QuickAnswerCacheService`：SNAPSHOT/PREBUILT/HOTSPOT 三层，命中靠 **5 组硬编码关键词** + confidence≥0.70，含"实时/最新"即跳过 → 命中率很薄
- **embedding 缓存是进程内 `ConcurrentHashMap`**（`QdrantService:142`，30min/500条）→ 多实例不一致、无失效通知
- **Qdrant 写入全是一条条 upsert**（`SchemaVectorManager:245`、`KnowledgeSearchTool:290`）→ 无批量

### 1.6 Agent 编排

全手写，无 LangChain/LangGraph：
- `agent/dag`（DagGraph/DagNode/DagExecutionEngine/SwarmExecutionEngine，节点默认 60s 超时）
- `agent/planning`、`agent/handoff`、`agent/skill`（110+ 工具，靠 `ToolDiscoveryRag` 向量挑选，≥30 个才启用）
- 主循环 `agent/loop/AgentLoopEngine.java`（1463 行）
- 多轮上下文：`ConversationMemoryService` + `ContextCompressor`（max-turns 20/compress-threshold 10/TTL 24h）

### 1.7 其他已识别短板

- `GroundedGenerationGuard:78` 用 `evidence.contains(num)` **字符串包含**判定接地率（阈值 0.8）→ 误判率高
- `GepaPromptOptimizer` 是**离线遗传算法**（每天 04:20，种群10/5代，适应度用历史评分+模拟、**不调 LLM**）→ 优化目标与真实效果脱节
- 超时分散：agent 180s / quick-path 15s / qdrant 10s / text-to-sql 15s
- Query 改写第 2 轮起**同步调 LLM，最多 3 轮串行** → 延迟叠加

## 三、差距分析（按影响排序）

| # | 差距 | 影响 |

## 四、升级方案（按 ROI）

### P0-1 · 开启并换掉 Rerank —— **采纳，立即做**

现状是「写了但关着」。两步：
1. 把 `ai.cohere.rerank.enabled` 打开前先**换 provider**：Cohere 是国外服务，延迟和合规都不合适
2. 改用**硅基流动 `BAAI/bge-reranker-v2-m3`**（与现用 bge-m3 同源、免费额度、国内直连）

做法：hybrid 召回 top-50 → rerank 精排 → top-5 喂 LLM。可在 top-1 分数够高时跳过 rerank 省时延。
**注意**：`CohereRerankService` 的调用点在 `KnowledgeSearchTool:248`，只覆盖工具检索路径；
主 RAG 链路（`AgenticRagService.retrieve`）**也要接上**，否则只治了一半。

### P0-2 · 修 sparse：加 IDF + 消灭哈希冲突 —— **采纳**

> **🟢 部分已就绪（D-389）**：`sparse-v2` 灰度开关已落地（`intelligence.qdrant.sparse-v2`，**默认 `false`**）。
> - 开启效果：去掉中文单字符噪声 + token 哈希从 10 万桶扩到 31 位
> - **默认关闭是刻意的**：改哈希与存量索引不兼容，若直接开启，查询侧新哈希与库里旧哈希对不上，
>   sparse 侧会完全召回不到（dense 不受影响，混合检索退化为纯 dense）
> - 开启步骤：①全量重建 sparse 索引 → ②置 `sparse-v2=true` → ③重启
> - 失败回滚：改回 `false` 重启即可，无需动数据

- **✅ 已做**：去单字符 + 扩大哈希（在开关后）
- **⬜ 未做 · IDF**：需要 df（文档频率）统计基础设施，且是**两阶段工程**
  （先全量写入建 df 表 → 再重建索引才能算 IDF）。成本高，未包含在此次改动。
- **替代思路**：直接删掉自研 sparse，改用 **Qdrant 原生 text index**（服务端实现的真 BM25，
  不需要自己维护 df）。若 Qdrant 版本支持，这比自研 + IDF 更划算 —— 需先确认版本。

替代方案：换 Qdrant 原生 BM25（服务端 sparse 推理），删掉自研 500 行。**倾向先修自研，成本低、可控。**

### P0-3 · 主链路接入混合检索 + 放大 top-k —— **采纳**

- `recall-top-k: 3` → **至少 20**（先召回够，再由 rerank 收窄）
- 主 RAG 从 `QdrantService.search` 切到 `hybridSearch`（`:406`），让日常问答也享受关键词精确匹配
- 服装场景的款号、色号、订单号是**强精确匹配需求**，纯 dense 天然劣势

### P1-1 · schema 向量独立 collection —— **采纳**

现在 schema 和记忆共用一个 `fashion_memory`，靠 `schema_` 前缀过滤。
拆成独立 collection，噪声立刻下降，也不需要前缀 hack。

### P1-2 · Text-to-SQL 加预校验与失败重试 —— **采纳**

- 执行前 `EXPLAIN` 预校验（语法 + 权限）
- 执行失败 → 把错误信息回喂 LLM 自修正（最多 2 次）
- few-shot 从「1 个静态示例」升级为**动态检索最相似的 N 个历史 SQL**

### P1-3 · Query 改写提速 —— **采纳**

现状第 2 轮起同步调 LLM、最多 3 轮串行 → 延迟叠加。
改：首轮并行发「原 query + 改写 query」两个检索请求，取优；改写失败不阻塞主链路。

### P1-4 · 语义缓存 —— **采纳**

`QuickAnswerCacheService` 现在靠 5 组硬编码关键词命中，很薄。
升级为**向量相似度缓存**：query embedding 与历史 query 相似度 > 0.95 → 直接返回。
对「今天有多少订单在生产」这类高频重复提问效果显著，省钱也提速。

### P1-5 · Qdrant 批量写入 + 缓存外置 —— **采纳**

- `SchemaVectorManager:245`、`KnowledgeSearchTool:290` 逐条 upsert → 改批量（Qdrant 原生支持 batch）
- embedding 缓存从进程内 Map → Redis（多实例一致 + 可主动失效）

### P2-1 · 流式真流式 —— **采纳**

`SpringAiInferenceAdapter:148` 的 `.blockLast()` 让 SSE 名不副实。改成真正的逐 chunk 推送，首字延迟立降。

### P2-2 · 接地判定升级 —— **采纳**

`GroundedGenerationGuard:78` 用 `evidence.contains(num)` 太糙。
改：数字归一化后再比对（"1,234" vs "1234"、"3件" vs "3"），或直接让 LLM 做一次接地性判断。

### P2-3 · Embedding 换 Qwen3-Embedding —— **观望，不采纳**

现用 bge-m3 已是 1024 维主流，与 reranker 同源且免费。
换模型要**全量重建向量**（3000 款 + 全库 schema + 记忆），收益不足以覆盖成本。
**先上 rerank，embedding 不动。**

### P2-4 · AutoLink 渐进式 schema linking —— **采纳，排后期**

AutoLink（AAAI 2026）发现：**全库 schema 一次性塞给 LLM 会稀释注意力，性能反而下降**。
等 P1 做完再评估：若单次召回 > 15~20 张表，就改 agent 渐进扩展。

### P2-5 · GraphRAG —— **不采纳**

适合文档型知识库。小云核心数据是**结构化业务表**，schema 关系已在数据库外键里，不必再从文本抽图。

### P2-6 · 引入 Mem0 / Zep —— **不采纳**

`LongTermMemoryOrchestrator` 已实现 mem0 核心思想（时间衰减 + 关键词 + 实体多信号）。
引入外部框架要重写记忆层 + 新增依赖，收益为负。
建议按 2026 记忆层五标准自查补漏：**能否按用户要求删干净（合规）、冲突事实怎么更新**。

### 🔴 单独立项 · Text-to-SQL root 数据源 —— **不在本次范围，但必须修**

`TextToSqlService:32-52` 用主数据源 root JdbcTemplate。这是**安全 P0**，
与检索优化无关，建议单独开一个修复项（只读账号 + 库级隔离 + 审计）。


## 六、一句话总结

> 小云的底座（3 轮自我修正 RAG、RRF 多工具融合、110+ 工具的 Agent 编排、多信号记忆衰减）
> 已经比多数团队的 RAG 系统完整。**缺的从来不是架构，是三件具体的事**：
> ① 把写好了却关着的 **rerank 打开**；② 让**主链路真正用上混合检索**（现在是纯 dense，top-k 还只有 3）；
> ③ 把自研 **sparse 从"伪 BM25"修成真 BM25**。
> 这三件做完，性价比远高于换 embedding 或上 GraphRAG。
