# 核实报告：领料出库事务边界缺口

> 核实时间：2026-10-01。核实方式：源码调用链追踪 + 注解存在性检查。
> **本文档只做核实，不含修改。** 结论待业务确认后再决定是否修复。

---

## 一、结论先行

| 路径 | 事务 | 判定 |
|---|---|---|
| **PC 端 BOM 领取**（主流程） | ✅ 有 | **安全** |
| `createPicking` / `MaterialPickingTool` | ❌ 无 | **有数据不一致风险** |

**主流程是安全的**，D-099 的修复真实有效。但存在一条**旁路**缺事务保护。

## 二、主流程核实：安全 ✓

PC 端 BOM 领料走：

```
MaterialPickingController:40
  └─→ MaterialPickingOrchestrator.createPending()
        └─→ MaterialPurchaseOrchestrator.createPickingAndOutbound()   ← @Transactional(rollbackFor = Exception.class)
              ├─ materialPickingService.savePendingPicking()   建单
              └─ pickingHelper.confirmPickingOutbound()        扣库存 + 出库日志
```

`MaterialPurchaseOrchestrator.java:889` 确有：
```java
@Transactional(rollbackFor = Exception.class)
public String createPickingAndOutbound(MaterialPicking picking, List<MaterialPickingItem> items) {
```

代码注释里 D-099 声称的"同事务：建单+扣库存+出库日志+采购单联动，库存不足会整体回滚"—— **属实**。

> 补充：`MaterialPurchasePickingHelper.java:679` 有一条注释

## 三、缺口：`createPicking` 无事务 ⚠️

### 3.1 问题代码

`MaterialPickingServiceImpl.java:37` 的 `createPicking()` 做 **4 个写操作**：

```java
this.save(picking);                                    // ① 写领料单（status 直接置 completed）
for (MaterialPickingItem item : items) {
    materialPickingItemMapper.insert(item);            // ② 写明细
    MaterialStock stock = resolveStock(item);
    materialStockService.decreaseStockById(...);        // ③ 扣库存  ← 会抛异常
    // 或 decreaseStock(...)
    recordOutboundLog(picking, item, stock, ...);      // ④ 写出库日志
}
```

**事务注解检查结果**：

| 文件 | `@Transactional` 次数 |
|---|---|
| `MaterialPickingServiceImpl.java` | **0** |
| `MaterialPickingOrchestrator.java:56` `createPicking` | **0** |

调用链上**没有任何一层开启事务**。

### 3.2 失败场景：会产生脏数据

`MaterialStockServiceImpl.java:184` 确认扣库存失败会抛异常：

```java
int rows = baseMapper.decreaseStockWithCheckDecimal(stockId, quantity, ...);
if (rows == 0) {
    throw new IllegalStateException("库存不足，扣减失败: " + name);
}
```

于是，在多明细领料单里，**第 2 条明细库存不足**时：

```
① save(picking)                    → 已提交 ✓ 领料单存在，status=completed
② insert(item1)                    → 已提交 ✓
③ decreaseStock(item1)             → 已提交 ✓ 库存扣了
   ── 处理 item2 ──
④ decreaseStock(item2)             → ✗ 抛 IllegalStateException
   ⑤ insert(item2) / 出库日志       → 未执行
```

**结果状态**：
- 领料单状态是 `completed`（"已完成"），但明细只有 1 条
- 库存扣了 1 条的量，出库日志缺失
- **无事务回滚** → 数据不一致，且用户看到的是"领料单已完成"

这与 D-099 修复的原问题是**同一类**（"只建单不扣库存"），只是发生在旁路上。

### 3.3 两个调用方都无事务

| 调用方 | 路径 |
|---|---|
| `MaterialPickingController:40` | → `MaterialPickingOrchestrator.createPicking()`（无事务）→ Service |
| **`MaterialPickingTool:133`** | → **直接调 `materialPickingService.createPicking()`**，绕过 Orchestrator |

⚠️ **两条都不在事务内。**

## 四、`MaterialPickingTool` 绕过编排层的问题

```java
// intelligence/agent/tool/MaterialPickingTool.java:133
String pickingNo = materialPickingService.createPicking(picking, items);
```

**项目铁律**（CLAUDE.md P0）：
> Services must NOT call each other — all cross-service orchestration goes through Orchestrator.

`MaterialPickingTool` 位于 `intelligence/agent/tool` 包，**直接注入 Service 做多表写入**，未走 `production/orchestration`。

**同包内是否有反例对照**：`PendingTaskOrchestrator`、`MaterialInboundOrchestrator` 等 AI 相关编排器都规规矩矩走 orchestration 包，`MaterialPickingTool` 是少数例外。

**这带来两个问题**：
1. 事务无人兜底（编排层是项目里 `@Transactional` 的唯一归属，见下）
2. 与 `MaterialPickingOrchestrator.createPicking` **逻辑重复** —— 同一个 Service 方法被两条路径调用，若未来修 `createPicking` 的事务只需改一处，但若新增字段/校验就会漏改一处

---

## 五、根因：事务归属被误解

统计全仓 `@Transactional` 分布：

| 包 | 文件数 |
|---|---|
| `**/orchestration/` | **160** |
| `**/service/` | 16 |

这印证 CLAUDE.md 的规则：**`@Transactional` only in Orchestrator layer**。

而 `createPicking` 这条链的**编排层方法恰好没加注解**——不是"Helper 层多加了"（那才是 D-001 修过的问题），而是**编排层漏了**。

---

## 六、修复建议（待确认，暂不动手）

### 方案 A（推荐）：编排层加事务

在 `MaterialPickingOrchestrator.createPicking()` 加 `@Transactional(rollbackFor = Exception.class)`。

- ✅ 符合项目事务归属约定（事务在编排层）
- ✅ 一处改动同时覆盖 Controller 与 AI Tool 两条路径
- ⚠️ 但 `MaterialPickingTool` 仍绕过编排层，事务靠"它调的那个 Orchestrator 方法"才生效——
  若 Tool 后续新增其他写操作，仍会漏保护

### 方案 B：Tool 改走编排层

`MaterialPickingTool` 改注入 `MaterialPickingOrchestrator` 而非 `MaterialPickingService`。

- ✅ 同时解决"绕过编排层"和"事务无归属"两个问题
- ✅ 与项目铁律一致
- ⚠️ 改动面：需确认 Tool 的租户上下文（`UserContext`）在编排层内仍能正确取到

### 建议 A + B 一起做

B 才是根治（消除旁路），A 是兜底（防止将来又有人直接调 Service）。
