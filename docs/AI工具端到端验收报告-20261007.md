## 三、🔴 坏掉的工具（查询了不存在的列）

**判定方法**：解析每个工具注入的 Mapper → 实体 → `@TableName` → 生产真实列，
再核对工具里 `.eq/.in/.groupBy/.orderBy` 等使用的列字面量。
**已逐列在生产库人工复核，排除 SQL 别名（`count`/`defective`）与跨 Mapper 误配等噪声。**

| 工具 | 表 | 查询了不存在的列 | 真实列名 |
|---|---|---|---|
| **`tool_quality_statistics`**<br>`QualityStatisticsTool` | `t_cutting_bundle` | `quality_status`（6 处）<br>`quality_remark`、`order_no` | 无该列（真实是 `status`）<br>真实是 `production_order_no` |
| **`tool_compliance_expert`**<br>`ComplianceExpertTool` | `t_cutting_bundle` | `quality_status`、`quality_remark`、`delete_flag` | 均不存在 |
| | `t_product_warehousing` | `factory_id` | 不存在 |
| **`tool_inventory_summary`**<br>`InventorySummaryTool` | `t_material_stock` | `style_no` | 不存在 |
| | `t_product_sku` | `material_type`、`quantity`、`locked_quantity` | 真实是 `stock_quantity`；无 `material_type` |
| **`tool_unit_price_query`**<br>`UnitPriceQueryTool` | `t_style_info` | `factory_name` | 不存在 |

### 为什么这是高危

这四个工具**已注册、可被 LLM 选中**（D-702 的「同域补齐」会按域拉工具），
一旦被调用就是 MySQL `ERROR 1054 Unknown column` → 用户看到工具失败。

### 附带发现：状态值与真实数据也不一致

`t_cutting_bundle.status` 真实分布（551 行）：

```
created 403　｜　qualified 145　｜　repaired 3
```

而 `QualityStatisticsTool` 用的是 `REJECTED` / `REPAIRING` / `REPAIR_COMPLETED` / `SCRAPPED`
—— **这些值在生产数据里一个都不存在**。所以这个工具不只是列名错，**整套状态模型都与实际数据不符**。

### ⚠️ 为什么我没有直接改

修法涉及**业务语义决策**，不是机械改列名：

- 该表**没有「不合格 / 报废」状态** —— 只有「待检 / 合格 / 返工完成」
- 因此 `defectiveRate`（不良率）、`scrapRate`（报废率）**在当前数据模型下没有对应数据**
- 若强行把列名改成 `status`、再猜一组状态值，会产出**看似合理但无意义**的指标
  （违反 CLAUDE.md 铁律 7：禁止伪造业务数据）

**建议修法**（需确认口径后执行）：把工具语义改为与真实数据一致 ——
`合格数 = status='qualified'`、`返工完成数 = status='repaired'`、`待检数 = status='created'`，
输出从「不良率/报废率」改为「合格率/返工率」。

## 四、🟠 静默失效的业务指标

**位置**：`BusinessSnapshotPrefetcher.countQualityIssues24h()`（第 185-193 行）

```java
"SELECT COUNT(*) FROM t_quality_inspection " +   // ← 这张表在生产不存在
"WHERE tenant_id = ? AND delete_flag = 0 " +
"AND inspection_result IN ('FAIL','UNQUALIFIED','DEFECTIVE','REWORK') " +
"AND inspection_time > NOW() - INTERVAL 24 HOUR"
```

- `t_quality_inspection` **不存在**（生产 289 张表里没有）
- `countWithSql` 有 try/catch 兜底返回 `-1`，**不抛异常、不报错**
- `fmtNum(-1)` → 渲染成 **「暂无数据」**

→ 结果：**每个租户**的业务快照里「近24小时质检异常」**永远显示「暂无数据」**，
AI 拿到的业务上下文长期缺这一项，且**没有任何告警**。

**同类错表名但无害的 2 处**（已核实，不必改）：

- `DatabaseHealthCheckJob` 的硬编码表名清单 → 有 `information_schema` 存在性守卫，不存在就 `continue`
- `DatabaseHealthCheckTool.TABLE_BUSINESS_NAMES` → 只作显示名映射用，未命中会走 `translateTableName` 兜底

## 五、SelfCritic「长期低分」追查结论

### 5.1 真实数据（`t_intelligence_feedback`，仅存低于阈值的样本）

| 指标 | 值 |
|---|---|
| 阈值 | `SELF_IMPROVE_THRESHOLD = 75.0` |
| 低于阈值的样本数 | 122 |
| 平均分 | **47.2**（最低 12，最高 75） |
| `agent_loop_quality`（走 Agent 循环、有工具） | 70 条，平均 **50.2** |
| `quick_path_quality`（快路径、无工具） | 52 条，平均 **43.1** |

### 5.2 三个关键结论

**① 「长期低分」很大程度是测量口径造成的。**
`autoSaveFeedback()` 只在 `overallScore < 75` 时写库 —— **这张表里只有失败样本**，
没有分母、没有通过样本。所以「查这张表 → 平均 47 分」**必然偏低**，
**不能据此判断回答质量在下降**。

**② 低分的结构性主因是「没有工具调用」，与 D-702 的诊断一致。**
`evaluateToolEfficiency`（权重 0.20）在「快路径 + 问题需要数据」时只给 **30 分**、
「无工具 + 需要数据」给 **50 分**。数据完全吻合：`quick_path` 43.1 < `agent_loop` 50.2。

**③ D-702 已经改善了它。** 按天看：

```
2026-10-04  agent_loop  45.5 (n=12)
2026-10-05  agent_loop  71.7 (n=3)   ← D-702 上线后
2026-10-06  quick_path  41.5 (n=2)
```

D-702（强制业务问题进 Agent 循环 + 工具可达性修复）上线后，`agent_loop` 分数
从 45.5 升到 71.7，**已接近 75 阈值**。

### 5.3 建议

- **不要调阈值**（团队此前的判断是对的）—— 调阈值只会掩盖问题
- **应该补分母**：把**全部**评分落库（或至少记录分数分布），否则「低分」永远无法判断真假
- `quick_path` 仍是低分来源，但 D-702 的「数据可信性闸门」已把业务问导向 Agent 循环，
  剩余 quick_path 主要是闲聊/知识问，给 30~50 分属**设计预期**，不是缺陷
