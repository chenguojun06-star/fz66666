> 触发：用户问「收银台是不是做得不专业，对比专业收银台系统看有没有优化」

## 零、先说一个事实

`t_pos_sale` 与 `t_pos_sale_item` **两张表都是 0 行** —— 收银台**写完了，但从没投入使用**。

模块规模：后端 8 个 java 文件（589 行编排 + 78 行支付回调 + 175 行写服务 + 7 个接口），
前端 1 个页面 856 行。

这个事实决定了评审的视角：**不是"哪里写错了"，而是"还没经过真实收银场景打磨"**。
很多缺失不是疏漏，是没被真实使用逼出来。

---

## 一、做得专业的地方（这些要保住，别在补功能时改坏）

| # | 做法 | 为什么专业 |
|---|---|---|
| 1 | **服务端算价，不信前端传的金额**（`checkout` 里逐条重算） | 避免「改前端就能改成交价」。这是零售系统最经典的漏洞，此处做对了 |
| 2 | **刻意不给 `checkout` 加 `@Transactional`** | 在线支付要在中间调渠道 HTTP 接口。把数据库事务挂在网络调用上，会长时间占着连接、渠道一慢就拖垮连接池。注释写明了原因 |
| 3 | **待支付中的单只是占位、不动库存** | 扫码后顾客不付钱是常态。若先扣库存，会产生大量"幽灵占库存" |
| 4 | **挂账强制填客户手机号** | 应收必须挂到客户名下，否则成了无主应收 |
| 5 | **复用既有的出库 / 应收 / 收付款中心**，不另建一套库存财务逻辑 | 避免两套真相源 —— 本项目正是因为在结构上有过两套真相源（Flyway vs 自愈清单）才吃过亏 |
| 6 | 扫码精确命中优先、上次成交价、`MAX_QTY/MAX_LINES/MAX_SEARCH` 上限 | 防「扫了 A 却加进 B」；老客不用重报价；防超大单 |

> **这几条比"功能多"更值钱。** 补下面的功能时，第 1、2、3、5 条一条都不能丢。

## 二、缺失的能力（按严重度排序）

### P0 —— 直接影响钱和账

**1. 没有班次 / 交班概念**

现状：`t_pos_sale` 只有 `cashier` 一个字段（谁卖的），
`/today` 查的是**全天**汇总。而专业 POS 的核心循环是：

```
开班（登记收银员 + 备用金）→ 收银 → 结班（系统账面 vs 实点现金）→ 长短款差异
```

没有班次，就答不上这几个问题：
- 这一班（比如 09:00–18:00）收了多少钱？
- 备用金 500，结班应该有多少现金？差了 20 是谁的问题？
- 换班时怎么交接？

**这是收银台最核心的缺失**，比打印、挂单都重要。

**2. 交班对账的时区 bug（已定位，一行可修）**

`PosSaleMapper` 的「今日按收款方式汇总（交班对账用）」用
`DATE(create_time) = CURDATE()`，而 MySQL `system_time_zone = UTC`、
应用按 `Asia/Shanghai` 写时间戳 → **每天 0–8 点，交班对账汇总的是前一天的钱**。
收银员是拿这个数去数钱的。同类 `CURDATE()` 共 10 处
（shop 今日统计 / pos / 今日扫码数 / 今日入库数）。

修法：JDBC URL 追加 `&sessionVariables=time_zone='%2B08:00'`，
只影响应用连接、不用重启数据库。

**3. 没有退款 / 冲正（销售退货）**

现状接口只有 `checkout` / `cancel-pay` / `pay-state` / `today`。
卖错了、顾客买了要退，**没有任何路径** —— `cancel-pay` 只是取消支付，
货没退、钱没退、库存没回。

而且 `crm` 域已有 `SalesReturn`（销售退货）表，
说明退货能力在建 CRM 时想过，但**没和 POS 打通**。

### P1 —— 影响日常好用程度

**4. 没有小票打印**（前后端均无 print / 小票）
线下门店顾客要小票，售后也常凭小票。可由浏览器打印 + 58/80mm 模板先顶上。

**5. 没有挂单 / 取单**
收银中顾客"再拿一件"是最高频场景。现在只能取消整单重来。

**6. 不支持组合支付**
`payMethod` 是单值。"微信付 80 + 现金 20" 这种混付很常见。
参考：改为 `t_pos_payment` 子表（一单多笔），`payMethod` 保留作汇总冗余。

### P2 —— 锦上添花，但服装零售常用

**7. 钱箱**（现金结算后弹开）
**8. 离线 / 断网续传**（门店网络差是常态；至少要做到断网可开单、恢复后补传，且要防重）
**9. 会员积分 / 储值抵扣**（`customer` 接口目前只返回客户信息和上次成交价）

## 三、建议的推进顺序

| 阶段 | 内容 | 理由 |
|---|---|---|
| **第一步** | 修时区 bug | 一行改动，立刻消除"对账算错钱" |
| **第二步** | 班次 + 结班对账 | 收银台的地基。建议新增 `t_pos_shift`（班次号、收银员、开班时间、开班备用金、结班时间、系统账面各收款方式金额、实点现金、长短款、状态），`/today` 改为**本班**口径 |
| **第三步** | 退款 / 退货，并打通 `crm.SalesReturn` | 已有表可复用，重点是库存回滚 + 原单关联 + 资金冲正 |
| **第四步** | 小票打印 + 挂单/取单 | 现场体验改善明显，实现也轻 |
| **第五步** | 组合支付（`t_pos_payment` 子表） | 动到数据结构，放后面 |
| **第六步** | 钱箱 / 离线 / 积分储值 | 按需 |

**每一步都要先补契约测试再动实现** —— 本项目 POS 目前 0 测试，
而这里每一行都是钱。参考 `OutstockReceivableHelperTest` 的写法：
每个"静默 return / 静默跳过"的 guard 都要有断言守着，
否则坏了就是「货出去了、账没记、钱丢了且没有任何报错」。

## 四、两个必须守住的底线（补功能时）

1. **服务端算价不许交给前端** —— 任何新增的"改价 / 折扣 / 议价"入口，
   折扣理由和授权必须落库，不能只在前端减个数。
2. **不要新建第二套库存 / 财务逻辑** —— 出库走 `freeOutbound`、
   应收走 `ReceivableOrchestrator`、收款走 `PaymentOrchestrator`。
   POS 只做编排。这也是现有实现最值得肯定的设计。
